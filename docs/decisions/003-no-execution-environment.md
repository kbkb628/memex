# 003 · 第一版不给文件系统和代码执行

- 状态：已采纳
- 日期：2026-11-03
- 影响范围：工具集、部署形态、以及这个项目能被用来做什么

## 背景

这个赛道上的成熟项目都有执行能力：Moltis 用 Docker / Apple Container 做沙箱，OpenClaw 是一整个宿主平台，gini-agent 能接管浏览器。对「personal agent」这个词，读者的默认期待里就包含「能替我动手」。

第一版没有这些。这是一个主动的减法，不是还没做完。

## 决定

不提供：

- 文件系统读写
- 命令执行
- 浏览器自动化
- 任何修改外部世界的工具

计划提供、但目前尚未实现的：只读的网络访问（抓网页、读订阅源）。在它落地之前，这个 agent 知道的一切只来自你打的字。

## 三个理由

**一、部署安全。**

这是一个要被别人 fork 到自己账号下的东西。如果它带着文件系统和 shell，那么每一个 prompt injection 都是一次远程代码执行——网页里藏一句话，就能让它读你的密钥、删你的文件。

只要工具全是只读的，注入最多让它说错话，偷不走东西。这个边界让「敢不敢部署」这个问题有答案。

**二、架构简洁。**

不给执行能力，就不需要容器编排、沙箱逃逸防护、文件同步、长连接心跳、崩溃后的环境重建。整个运行时是一个 Durable Object，没有别的进程。

这不是省钱的问题，是**能读懂**的问题。一个读者花二十分钟能看完所有代码，才有资格谈「架构判断」。

**三、竞争位置。**

在执行能力这个维度上，比不过一个 27 万行 Rust、59 个 crate 的项目。硬要比，只会显得单薄。

不如把边界划清楚：它在「在线、零运维、记忆可信」这个象限里工作，不在「沙箱执行、全天候干活」那个象限。

## 代价

**演示价值低。** 试用者打开之后，五分钟内很可能得出「这不就是 ChatGPT 加个记事本」的结论。

这是真实的损失。执行能力是最直观的说服力，而记忆的可靠性需要时间才能感受到——它只在第十次对话、当模型开始把自己的旧推断当前提的时候才显形。

缓解方向是只读网络访问：能让它读到你丢过去的链接、能每天自己看几个源，试用体验会完全不同。但那解决的是「有没有东西可想」，不是「能不能动手」。

## 什么时候该重新考虑

有一个具体的、非执行不可的任务时。判断标准要具体：

- 「这周有三件事必须它自己跑」→ 该做
- 「以后可能会用到」→ 不该做

如果决定要做，优先选远端沙箱（Cloudflare Containers 或类似方案），而不是反向隧道连回本地机器。后者听起来更强大，实际上把「部署安全」这个前提整个推翻——别人的 agent 能连到别人的笔记本，那是另一个威胁模型。
