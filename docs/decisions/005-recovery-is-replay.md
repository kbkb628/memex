# 005 · 恢复的语义是「重新执行」，因而副作用必须幂等

**状态**：已实测
**日期**：2026-11-04

## 背景

「关掉页面也不丢」这句主张，在只有假 key 的情况下没法验：假 key 一秒内就以 `model_error`
结束，任务根本没真正跑起来过。所以第一次拿真 key 跑，验的不是「能不能答」，
而是**跑到一半被杀之后，它到底还认不认这件事**。

## 实验

```
提交一条 5000 字任务 → 立刻 GET /op = running
→ taskkill /F /IM workerd.exe      杀掉真正执行 DO 的进程
→ 端口返回 000，服务彻底消失
→ 同一条命令内拉起新实例，从第一秒开始计时
```

结果：

```
+2s … +28s   running（57B，无正文）
+30s         done（14877B，12 节，5299 字）
```

答案是在重启之后生成的。断电时那条任务只活了不到两秒，物理上写不出 5000 字。

## 顺带记一个让实验连续假阳性两次的坑

`taskkill` 打的是父进程 `node`，而真正跑 DO 的是子进程 `workerd.exe`。
父进程死了，子进程还在，任务照跑完，结果照写进 SQLite。于是重启新进程一查就是
`done`，看起来像「秒级续跑成功」，其实是同一个进程从没死过。

**判断「进程真的死了」不能看 `taskkill` 的返回码**，要看两件事：`workerd` 还剩几个、
端口还在不在 `LISTENING`。TIME_WAIT 不算——它只说明连接断了。

## 结论

pi-durable 的恢复是**从头重新执行**，不是从上次的半个输出往下续写。
+2s 到 +30s 全是 `running`、没有中间结果，最后一次性 `done`，这就是重跑的形状。

这不是缺陷，是语义选择：它给的是「至少一次」（at-least-once），
保证事情最终有结果，不保证已经生成的 token 不白费。

## 后果

1. **纯生成类任务可以放心重跑**：多花一份 token，结果一样。
2. **有副作用的动作必须自带幂等键**：发邮件、付款、提交表单，重跑就是重复执行。
   这不是要靠框架兜底的事，是每个写操作在设计时就得回答的问题——「如果它被执行两次，
   系统还对不对」。
3. **验证顺序因此固定**：不丢 → 不重复 → 更懂 → 自己会醒。跳过第二步去加工具，
   就会做出一个「偶尔发两封一样邮件」的 agent，而这种 bug 在演示里永远看不见。

## 什么情况下该推翻

如果将来加的第一个写操作工具，其副作用本身天然幂等（比如 `PUT` 覆盖写一个固定路径），
那么第 2 条可以放宽到「记录下执行过的键就够」。但只要出现任何一次不可撤销的动作，
这条就重新变硬。
