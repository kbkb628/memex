# 001 · 一个 Durable Object，不做 Router / 隔离 Worker 两层

- 状态：已采纳
- 日期：2026-11-03
- 影响范围：整个运行时结构

## 背景

多入口 agent 的常见做法是两层：一个常驻的 Router 收所有消息、做意图判断和准入控制，再把任务派给隔离的 Worker 执行。这套结构解决的是「多个用户、多个入口、并发任务互相不阻塞」的问题，代价是要处理跨进程的状态同步、任务归属、失败重派。

个人 agent 的约束完全不同：一个用户、三到五个并发任务、没有同事要协调。

## 决定

一个用户对应一个 Durable Object，全部入口的消息都写进同一个对象。

在这个对象内部，用 pi-durable 的会话机制模拟原来的两层：

- `root` 会话（id `"1"`）承担 Router 的角色，所有消息先进这里
- 需要动手的活 `sessions.fork(ROOT)` 出一个新会话，root 不被阻塞
- fork 出来的会话继承 root 的上下文，但不共享执行状态

Durable Object 本身是单线程、单写者的。这个性质在分布式系统里通常是限制，在这里是免费的保险。

## 放弃了什么

**水平扩展。** 一个对象跑满就是跑满，不能像无状态 Worker 那样加副本。对一个用户来说这不是问题，对一千个用户就是致命的——那时应该是「一个用户一个对象」，而不是「一个对象扛所有用户」。现在的 `idFromName("me")` 写死了单用户，这是刻意的。

**独立配额与权限边界。** 两个 Worker 可以是两个不同的 Durable Object 类，挂不同的限流和工具集。单对象做不到，所有能力共享同一个预算。

**不受信代码的隔离。** 如果将来要跑用户提供的脚本，必须有独立进程或容器。这个对象里没有那层边界。

## 换来的东西

一台机器、一个写者、一份状态。多设备场景下最折磨人的几类 bug 在结构上不可能发生：

- 两个分身各记一份，都以为记下来了
- 文件同步了但索引没更新，读到的版本不一致
- 一个分身否定了某个方案，另一个不知道，继续按旧前提推

这些不是「更难发生」，是没有地方发生。

## 什么时候该重新考虑

三个信号，出现任意一个就该拆：

1. 需要两种权限级别（例如「能读记忆」和「能改记忆」必须是两个主体）
2. 需要给不同任务设独立预算，且预算要能被平台强制
3. 要执行不受信的代码

在那之前拆分，是在给自己造分布式 bug。
