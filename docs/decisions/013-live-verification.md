# 013 · 线上那一档从公网发起，因为开发机根本到不了那里

**日期**：2026-11-07
**状态**：已落地

## 问题

验收分三档：本地 workerd、部署成功、部署后的真实请求。前两档一直是绿的，第三档一直空着，理由是「`*.workers.dev` 在国内被 DNS 污染」——听起来像个无奈的客观限制，但从来没查过它到底限制在哪一层。

今天查了：

```
本地 DNS 解析          → 108.160.165.212     ← 污染值
DoH（alidns）查真实值   → 173.255.209.47
--resolve 直连真实 IP   → 15 秒超时
另试五个边缘段          → 104.16 / 172.67 / 162.159 / 188.114 / 104.24 全部 000
本机代理               → github.com 可以（证书撤销检查报错但链路通），
                         workers.dev 直接 CONNECT 502
```

结论比预想的更硬：**不是解析错了，是这台机器到 Cloudflare 边缘整体不可达。** 换 DNS、指定 IP、走代理，三条路都堵死。

那「这一档验不了」就不是结论，而是个待办：要么换个网络，要么换个发起方。

## 决策

加 `.github/workflows/live.yml`，手动触发，从 GitHub 的 runner 发起。`scripts/live-check.mjs` 只发 HTTP —— 它验的是「部署出去的那一份在公网上真的能应答、真的能跑完一个任务」，和 `receipt.mjs` 验的「代码在 workerd 上活不活得下来」是两件事，都成立才算完整。

断言 17 条，覆盖：公网可达、鉴权真的生效（不带 token 401）、状态完整、排期存在、巡检真的醒过、任务跑完、幂等在公网这一层也成立、目标能推一轮。

**不进 push 流程**，只能手动触发：它打的是线上实例、会花真 token，不该每次提交都跑。

**不用 `npm ci`**：脚本只用 node 自带的 `fetch`，不碰依赖。少一步依赖安装，这一档就少一种「因为装不上所以没验」的失败方式。

## 几个不显然的地方

**「排期存在」和「到点真的醒过」是两件事。** 第一次跑时实例刚部署，`/patrol` 只能给出 `next`（1 分钟后）。那只证明 job 排上了。等那一轮真的到期执行、第二次跑读到 `last.at = 2026-11-07T10:54:53.125Z`（`scanned: 2`）时，才有了醒过的证据——而且这个时刻和第一次看到的 `next` 对得上。

所以脚本写成两条路：有 `last` 就断言它，没有就看 `next` 够不够近、够近（三分钟内）就等。**超过三分钟的不等**——巡检一天一次，等不起，也不该假装验过。

这份证据是**跨两次运行**拼起来的。只跑一次的凭证说明不了「它会自己醒」，只说明「它排了个期」。

**发起方必须写进凭证。** `deploy.from` 记的是 `github-actions (<runner>)`。读这份 JSON 的人默认会以为是在开发机上打的，不写清楚就是在借别人的网络冒充自己的环境。

**token 交出去是有代价的。** 为了从 runner 访问，`MEMEX_TOKEN` 进了仓库 secret —— 等于把「能读写这个私人 agent」的凭证交给 GitHub 保管。对演示仓库可以接受（token 可随时撤换），但对真的私人部署，这是要重新权衡的一件事，不该默默做掉。

## 代价

**线上只覆盖 17 条主链路**，本地那套杀进程、断电续跑、预算拆账的演练在线上一条都没做。这两档不能互相替代。

**线上和本地不是一份数据。** DO 的 SQLite 各存各的，线上的会话号、收件箱、目标都只属于线上那个对象。因此「本地 61 条会话」这种说法不能挪到线上用。

**依赖 GitHub 的可用性。** 这条链路要跑起来得有网、有额度的 GitHub Actions。它不是本地能复现的验收——这也是它只能算「补充了一档」而不是「补全了验收」的原因。
