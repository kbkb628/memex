# 010 · 默认带三个源；基线靠「有没有 seen 记录」判定，不靠「加源」这个动作

**状态**：已实测
**日期**：2026-11-06

## 背景

009 把输入源做出来了，但一个刚部署的实例是空的：`cfg:feeds` 不存在，收件箱永远是空的，`/ingest` 的报告写着「还没有配任何源」。

这件事有两个层面的问题：

1. **体验层面。** 第一次打开看到一个空收件箱和一句「去配源」，等于把配置成本推给用户。他得先读 README、找到 `/feeds` 的接口、编一句 `want`、再回来刷新。绝大多数人到这里就关了。
2. **证明层面。** 这个项目的主张是「它自己会醒、自己判断」。空实例一个证据都不给，主张就只能靠读代码相信。

同时还有第二个问题：基线只写在 `addFeed` 里。也就是说「不吃历史」这件事依赖于**用户走了加源这条特定路径**。任何其他产生源的方式（默认值、迁移、手工写库、`seen` 记录被删）都会绕过它，直接触发一次洪水。

## 决定

**开机时把三个源写进配置，基线判定改成「这个源有没有 `seen:` 记录」。**

三个源是 Cloudflare 博客、HN 首页、阮一峰的网络日志。都不是随便挑的：它们的更新频率差异很大（一天几条 / 一天几十条 / 一周一条），正好能压测预算闸门在不同节奏下的行为。

判定改成：

```
seen 记录不存在  → 这一轮只记基线，全部记为已见，一条都不发
seen 记录存在    → 正常比对，只提交没见过的
```

## 为什么

**为什么不是「第一次巡检时全部提交」。** 一个每天更新 20 条的源，第一轮就是 20 条，当天预算（20 次）一把烧完，用户看到的是 20 条历史文章，而且当天再也收不到新的。体验比空收件箱还差。

**为什么基线不放开机时做。** 开机在每条请求的必经之路上（`ensureJobs`），抓三个源要联网，慢了直接拖慢页面。而巡检本来就允许慢（`hungTimeoutSeconds: 90`），它才是该干这个的地方。

**为什么用 `seen` 记录的存在性当判据，而不是加一个 `baselined: true` 标记。** 前者是自愈的：`seen` 记录就是基线本身，它丢了就重建，不存在「标记说有基线、实际没有」这种半状态。多一个标记就多一处可能不一致的地方。

**为什么删掉默认源之后不补回来。** 判据是 `cfg:feeds` 存不存在，不是长度。用户把三个源全删了会留下一个空数组，那是「我不要这些」的意思。用长度判断会变成「你删干净了，我下次开机再给你装回来」。

## 代价

- 新实例开箱就不再是空的，但也意味着**默认值构成了第一印象**。三个源都是英文技术内容，对一个不读英文的人没用。这一点接受：默认值是「证明它能工作」，不是「猜你的口味」，删掉换成自己的只要两次请求。
- 多了一次存储读（`ensureDefaultFeeds` 里的 `get`）；在巡检路径上每轮一次，可忽略。
- `IngestReport` 多一个 `baselined` 字段。有它才能区分「今天真没新东西」和「今天刚接上基线」——这两种情况在旧报告里都是 `fresh: 0`，看起来一模一样。

## 实测

```
新实例第一次 GET /feeds     → 3 个源，id 与手工 addFeed 用同一个 hash
第一次 POST /ingest/run     → failed: [], fresh: 0, submitted: 0, baselined: 3
                              note: "3 个源是第一次接上，这一轮只记基线、一条都不提交"
第二次 POST /ingest/run     → baselined: null（没重复基线）
源里真的出现新条目          → fresh: 14, submitted: 3（预算只剩 3 次）
再醒一次                    → settled: 3, skipped: 2，收件箱里两条 ready
```

最后一行是重点：跳过的那 2 条**留着**，`?all=1` 能看到理由。基线机制不能顺手把留痕也省掉。

> 后来默认源换过一次：HN 首页被三组关键词订阅替掉，理由见 [014](014-oriented-sources.md)。这一篇里的机制（基线、不自动补回）没有变。
