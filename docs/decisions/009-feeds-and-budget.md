# 009 · 输入源只负责发现，判断交给任务；跳过必须留痕

**状态**：已实测
**日期**：2026-11-06

## 背景

007 之后它会自己醒了，但醒来看的是自己——扫一遍回执，看谁卡住了。那叫自我体检，不叫主动性。

主动性需要三样东西同时成立：**一个外部输入源、一道预算闸门、一个出口**。缺任何一样，做出来的东西都会坏在特定方向上：

- 没有输入源，它只是在空转。
- 没有闸门，它会自己把 token 烧完，而且你事后才知道。
- 没有出口，它看到的东西留在数据库里，只有你 curl 的时候才存在。

## 决定

**输入源用 RSS / Atom，出口用页面上的收件箱，闸门是每天 20 次调用。**

### 为什么是 RSS 而不是邮件

邮件更贴近真实的痛点（报销、退款、客服都在邮箱里），但**邮件要凭据**：IMAP 地址、应用专用密码、有些还要开两步验证。

RSS 只是一行 URL。

这不是技术取舍，是分发取舍：**门槛决定了别人会不会真的用起来，而不只是能不能用。** 一个填 URL 就能开始的东西，和一个要先翻邮箱设置页找应用密码的东西，用户量差一个数量级。

### 结构：发现与判断分离

这是整个设计的核心，而且它是被物理约束逼出来的，不是审美选择。

`lifecycle.jobs` 的 dispatch 有超时预算（`hungTimeoutSeconds` 默认 30 秒）。四条实验、几篇文章的模型生成，任何一条都能把这个预算撑爆。所以：

```
醒来（onJob，90 秒预算）
  ├─ 1. 结算上一批：跑完的搬进收件箱          ← 只读状态，不调模型
  ├─ 2. 看今天还剩几次预算                    ← 一次 storage 读
  ├─ 3. 拉每个源、解析条目                    ← 网络，几秒
  ├─ 4. 和已处理过的 id 比对，只提交真正新的   ← 字符串比较 + 落盘
  └─ 结束，排下一次

真正读文章、判断值不值得看 → 走 pi 的普通任务
```

第 4 步提交的是 `harness.submit()`，和用户在页面上打一句话完全同一条路径。

**这带来一个很大的好处：输入源没有引入任何新的执行机制。** 断电恢复、会话隔离、回执可查，这些对「它自己发现的」和「你让它做的」是同一个答案。如果在这里另起一套执行路径，那三件事都得重写一遍，而且会各写错一次。

### 闸门就是产品定义

```
每天最多 20 次调用 / 单次最多提交 5 条
```

这两个数字不是省钱手段。

它逼着这个东西承认「我一天只打算跟你说几件事」，于是它必须挑，不能搬运。**一个不设上限的订阅 agent，三天就会变成你最不想打开的那个 App。**

而因为「有没有新条目」是纯字符串比较，日常开销可以接近 0：一个每天更新 20 条的源，朴素做法是每天 20 次调用，这里是 0 次——直到真的出现没见过的 id。

## 两个踩出来的坑

### 一、跳过被静默删除

第一版在模型输出 `SKIP` 时把整条记录删掉，理由很自然：「跳过的东西不该占空间」。

结果出过一次事：模型把一条明明相关的内容判成 SKIP，而我在界面上看到的只是「收件箱是空的」。这有两种完全不同的解释——

1. 今天真的没有新东西
2. 它判断错了

**而删记录让这两件事长得一模一样。** 我看不到它跳过了什么，也就没机会去改 `want`。

改成保留记录、`state: "skipped"`、带模型的理由，`GET /inbox?all=1` 能看到全部。

**看不见的跳过等于没有发生过。** 这条不只适用于这里：任何「系统替你做了决定」的地方，决定本身必须是可见的，否则用户永远学不会怎么用它。

### 二、`want` 写成关键词，模型就真的只匹配关键词

我第一版写的是「持久执行、Durable Objects、数据库一致性」，prompt 是「判断这条内容是否命中关注点」。

拿一篇《为什么你的定时任务会悄悄死掉》去测，它判了 SKIP，理由写得非常准确：

> 它不涉及持久执行（durable execution）机制、Durable Objects、数据库一致性中的任何一个——摘要没有提到工作流状态持久化、事务性或一致性模型。

**它没错，是我说错了。** 我想知道的是「这事值不值得我看」，而我写的是一串技术名词。

修正两条：

1. 判断标准写成「内容实质」，明确告诉它不要按词匹配。
2. 兜底方向反过来：**拿不准就报**。原来是「拿不准倾向 SKIP」，那是在用漏掉换安静；而多一条只是多扫一眼，漏掉的那条永远不会浮出来。

后来用同一篇文章（want 改成「个人 agent 的产品形态、身份与访问控制」）重测，它给出的结论里有原文没直说、但确实成立的东西：

> 它也直接指出纯 OAuth scope 思路不够用，因为「scope=全部」对站点零信息量，这是做 agent 权限设计时容易踩的坑。

## 加源不吃历史

接入时把源里现有条目**全部**记为「已见过」，一条都不提交。

不这么做的话：你填完 URL，它立刻把 20 篇文章倒进收件箱，当天预算一次烧完，而你还没看到一条有用的。**第一次使用的体验会直接决定你会不会用第二次。**

基线之后它才开口。第一次开口就是真的新东西。

## 实测

```
加源（Cloudflare 博客）→ baseline: 20，一条没提交，预算仍是 0
源更新，多出 2 条       → fresh: 2, submitted: 2，原有 3 条一条没动
等它们跑完再醒一次      → settled: 2, skipped: 1
```

结算出的命中项，它自己读了正文（摘要不够时模型主动调了 `fetch_url`），写出来的内容有三段：讲了什么、为什么值得看、**不确定的部分是什么**。

跳过的项留下了理由，包括那条被误判的——而看到理由之后我做的第一件事就是去改 `want`。

从界面加源的完整链路也走了一遍：填 URL 和 `want` → 点接入 → 拉取 → `baseline: 3` → 提示显示在页面上。

## 代价

- **3 小时是写死的常量。** 真实需求会是「这个源一天看一次就够，那个要每小时」。那时候周期得变成每个源自己的字段。
- **预算的时区偏移写成常量**（+8）。一个人用的东西，改一行比加一个设置页便宜。
- **它会自己读正文。** 摘要不足时模型主动调 `fetch_url`，判断更准，但一条内容的 token 可能是纯摘要的三四倍。这是它自己的选择——`SYSTEM` 里只写了「需要看某个页面才能回答时就自己取」。
- **收件箱有上限（200 条）。** 清理顺序是先删跳过的、再删已读的、最后才动没读的。跳过记录是增长最快的那部分。
- **12 个源是上限。** 多到这个数已经不是「挑」了。

## 什么情况下该推翻

- **需要一个真正的出口**（邮件 / IM 推送）。那会引入凭据，也就会劝退一半 fork 的人，所以要先想清楚出口是不是只对自己开。
- **如果 pi 提供了带独立超时预算的 job 类型**，第 4 步可以直接在那里等模型，架构会简单一层。现在这个「发现与判断分离」完全是因为 30 秒的物理约束。
- **如果 RSS 之外出现了一个同样不要凭据的输入源**（比如公开的仓库事件流），它的接入方式应该和这里一样：只发现，不判断。
