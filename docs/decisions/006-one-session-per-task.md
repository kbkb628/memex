# 006 · 一个任务一个会话，不做全局聊天窗口

**状态**：已实测
**日期**：2026-11-04

## 背景

第一版把每次提交都塞进 root 会话（`"1"`），原因是它最省事：`submit(text, { session: "1" })`
一行就完事。代价在跑了几条之后才显出来：

- **每句话都在为前面所有不相干的任务付 token。** 第 10 条消息的上下文里，躺着 9 条已经答完、
  再也没有用处的问答。
- **跑几十条就顶到上限。** pi 会裁剪，但裁剪意味着某天它悄悄丢掉了你以为它还记得的东西。
- **并发会互相污染。** 两个任务同时提交，第二个变成第一个的 `followUp`，答案里混进另一件事。

这不是配置问题，是模型选错了：把 agent 当成了一个聊天窗口，而它实际处理的是**一件一件的事**。

## 决定

每次 `/submit` 新建一个会话，这条任务终身独占它。

关键实现细节（不看源码会踩）：

1. **会话 id 不能自己编。** `conversationId()` 要求 `Number.isSafeInteger(id) && id >= 1`，
   传 `"op-xxx"` 直接抛 `Invalid pi session`。id 由 `harness.sessions.create()` 分配，
   root 是 `"1"`。
2. **所以幂等不能靠派生 id。** 必须「先查回执，有就回到原会话，没有才 create」。
   DO 单线程，这个「查-建」之间不会插进另一个请求。
3. **`pending()` 和 `wait()` 必须带 `{ session }`。** 不带参数时 pi 只查 root 会话，
   所有非 root 的任务都会查成空——表现为「任务永远 running」或「明明跑完了却查不到」。
4. **回执里要存 session。** `Note` 加一个 `session` 字段，否则查回执时不知道该去哪个会话找。

## 实测

```
提交 A「用一句话描述日落」                    → session 52
提交 B「我上一条问了你什么？看不到就答看不到」  → session 62
两者同时 running
A → done：太阳沉到地平线下，把半边天烧成橘红…
B → done：看不到
/status → sessions: 3（root + 2）
```

B 看不见 A，隔离成立；A、B 同时在跑，并发不阻塞。
重投 A 的 `operationId` → `accepted: false`，`session` 仍是 `52`，会话数仍是 3。
断电重启后，`dyn-001` 从 session 74 恢复并跑完 5511 字。

## 后果

**好处**：上下文恒定、并发天然隔离、恢复边界清楚（一条任务只恢复自己那条线）。

**代价一：会话之间不共享记忆。** 追问「刚才说的那个再详细点」不会生效。
这是有意的——真要做连贯对话，正确做法是在提交时把上一次的结果当 `handoff` 带进去，
而不是把它们塞回同一个会话，因为后者的成本是随时可能爆掉的上下文。
第一版不做，因为没有真实需求支撑，做了只是给自己加复杂度。

**代价二：会话只增不减。** pi 没有删除会话的接口（`PiSessions` 只有 `get` / `create` / `fork`）。
一条任务几 KB，5GB 存储能装十万量级。一个人用够了，但这是笔明账，得写在 README 里，
不能等别人 fork 走之后自己撞上。

## 什么情况下该推翻

如果真实的用法变成「一件事要来回问十几轮」（比如调试、写长文反复改），
那么一任务一会话会让每一轮都从零开始，体验不可接受。
那时应该改成：一个会话承载一个**话题**，话题结束时 `reset(handoff)` 把上下文压成一段摘要，
而不是按提交次数切。判断依据是「用户会不会对同一个东西持续追问」。
