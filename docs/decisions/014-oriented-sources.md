# 014 · 换源，而不是继续调词表

**日期**：2026-11-07
**状态**：已落地

## 问题

默认源里的 HN 首页是「所有技术话题」的首页，不是「我关心的话题」的首页。为了让它能用，我配了 62 个词的粗筛（011）。量了两天，结论是这条路到头了：

```
累计回放 33 条判断：误杀 0 · 放行且有关 9 · 白放 16 · 正确挡掉 6
配了词表的 31 条里喂给模型 25 条 —— 只省 19%
```

一天 20 次调用，下午就见底；额度一见底它当天就不再干活，用户看到的是「它停了」。

两个假设被数据否掉：

**一、不是链接 slug 撞词。** 拆成标题 / 路径 / 域名三处分别量：只在路径命中 4 条（其中 2 条真相关），标题命中 17 条（其中 12 条无关）。噪音压倒性来自标题。

**二、加否定词救不了。** 真正的洞是 `ai` 这个词在 HN 标题上已经失去区分力 —— 大多数标题都含它，一命中就放行，等于没筛。否定词只能补几个明确类别（IPO / 招聘 / 估值），补不动整体。

## 决策

**默认源里删掉 HN 首页，换成三组 hnrss 关键词订阅：**

```
https://hnrss.org/newest?q=%22durable+objects%22&points=20   → 19 条
https://hnrss.org/newest?q=%22agent+runtime%22&points=20
https://hnrss.org/newest?q=%22llm+agent%22&points=20
```

**把「筛」这个动作从判完之后挪到抓取之前。** 同样一天，`durable objects` 那组回来 19 条，几乎条条对题：

```
Show HN: Durable Actors – OSS Durable Objects with configurable compute
Open Source Durable Objects for Postgres
Why we're moving off Cloudflare Durable Objects
Durable Object alarm loop: $34k in 8 days, zero users, no platform warning
```

这些不是「恰好含某个词」，是**这条内容本身就长在这个领域里**。区别在于：词表是在读完之后猜它有没有关，关键词订阅是让对方替我们先筛一遍 —— 而且是免费的。

`points=20` 是第二道筛子。让分数替我们回答「有没有人觉得这条值得看」，替掉的是原来靠模型判断的那一层。

**粗筛机制保留，默认不启用。** `PREFILTER_AGENT` 那张表还在：谁自己想加一个泛话题源，可以直接拿去用，不用从头想。但没有默认源配它了，所以 `prefilter-check.mjs` 在没有可回放的源时会明说「没检查」，而不是打印「误杀 0、通过」——把「没检查」说成「检查没问题」是最坏的一种诚实。

## 顺带补的：抓取重试一次

三个默认源现在都走 hnrss，而它偶发 502。一次抓不到，这个源就要等下一轮巡检（三小时）。

所以 `fetchFeed` 加了：**5xx 和网络错误重试一次，4xx 不重试**（那是地址本身的问题，重试只是多打扰对方一次）。

这条有确定性的测法，不靠运气：`scripts/feed-check.mjs` 起一个本地桩服务，造出「第一次 502、第二次 200」，并数请求次数断言「确实只重试了一次」。9/9。

不测的话，写错了没人知道 —— 线上表现只是「偶尔某天少一个源」，看起来像对方的问题。

## 代价

**量小很多。** 换之前一天十几条进判断，换之后可能一天零到两条。这是选择的直接后果，不是缺陷：personal agent 的价值在「它替我挑到了什么」，不在「它今天看了二十条」。但要有心理准备——它可能连着两天没东西给你。

**刚发出来、还没攒到 20 分的帖子永远看不到。** `points` 门槛的代价。对「发现新东西」是损失，对「别拿垃圾烦我」是收益。

**只有英文、只有 HN。** 三个源都是同一家、同一种语言。这和「一个免费账号就能跑」是同一个取舍：不引需要密钥的源。

**hnrss 是单点。** 它挂了，三个源一起哑。重试只能救偶发 5xx，救不了长期不可用。

**老实例不会自动换。** 判断依据是 `cfg:feeds` 存不存在（010），不是内容。已经跑起来的实例要手动换：

```bash
curl -X POST $BASE/feeds/remove -H 'content-type: application/json' -d '{"id":"<HN 首页的 id>"}'
curl -X POST $BASE/feeds -H 'content-type: application/json' \
  -d '{"url":"https://hnrss.org/newest?q=%22durable+objects%22&points=20","label":"HN · durable objects","want":"..."}'
```

够不到那台机器的时候用 `scripts/sources.mjs`（列源 / 补默认源 / 按 URL 删一个），`live.yml` 里对应一个 `migrate_sources` 布尔输入。这次线上就是这么换的：

```
删掉 HN 首页，连带清掉 0 条收件箱条目
  加上 HN · durable objects（基线 19 条，一条都不提交）
  加上 HN · agent runtime（基线 9 条）
  加上 HN · llm agent（基线 20 条）
· 线上状态 — feeds: 5，19/19 仍然全绿
```

`--drop` 必须显式给 URL，不给就一个都不删：删源会连带删掉那个源在收件箱里的条目（009），这种能力不该藏在一个默认行为里。

换源等于把「HN 首页的判断历史」一起清掉（这就是上面那句 0 条要写出来的原因：清了 0 条，说明那边本来就没判断过什么）。本地那台清掉了 31 条，所以换之前先跑了一次 `prefilter-check` 存进 `receipts/prefilter.json` —— 那份凭证现在是那段历史的唯一痕迹。

## 没做的事

**「同时命中两个词才放行」没试。** 它可能在「保持召回」和「提精度」之间有个更好的点，但它解决的问题现在已经被换源绕过去了，不值得为它再调一轮词表。

**没有换成「更多领域的源」。** 一个只盯 Cloudflare / agent 运行时的 agent，对做这件事的人来说是对的；对别人不是。默认源是给人改的起点，不是产品边界。
